# 规划优化分析：先减少重复计算，再改善长尾策略

本轮只做分析和独立 CPU 诊断，未修改正在运行的生产配置、源码或任务。
诊断 owner：`db2e5a1902d64a1ab301eb9eb9c65cf7`，使用一个 nice=10 的低优先级进程。
复用冻结的深度、标定、起点、目标框和NavMesh，无模型调用、Simulator或实际运动。

分析对应生产owner `07b292f5809149419d11209f5dc9116b`。生产运行中的样本仍在增长，
下面各统计注明其样本量，不把不同取样窗口混为同一批任务。

## 结论与成本分布

在3764个已结束规划阶段中：

| 阶段 | 平均耗时 | 备注 |
| --- | ---: | --- |
| 整个规划阶段 | 7.19秒 | 中位数2.60秒，P95 41.85秒 |
| 生成框内候选之前 | 1.60秒 | 当前包含全图地面检查、mask保存和候选生成 |
| 候选生成之后 | 5.59秒 | 搜索、平滑、预演、安全验证及结果收尾 |

其中3008个最终成功记录的规划均值3.92秒；86个预算耗尽任务仅占2.28%，
却占约29.5%的规划阶段累计时间。不能用成功任务的平均值代替规划池的真实负载。
这些耗时来自不可变文件的mtime，包含调度/编码/落盘，不是纯CPU函数时间。

另一次5302条提交的metadata统计中，从冻结目标到规划claim平均约18.19秒，
P95 30.02秒，包含调度等待与输入构建；5163条已完成region selection到最终规划
回执的平均间隔约0.57秒、中位数0.10秒、P95 2.80秒。收尾有优化空间，当前优先级
低于几何计算与候选重复搜索。

## 一、普通任务固定支付整张图的地面检查

`ground_region` 先调用 `safe_floor_mask` 检查选定视角的整张480×270深度图，
然后才截取模型bbox里的支持点。实际候选与允许的目标调整都只使用原框内支持。

128条按case排序均匀间隔抽取的已结束任务中：

- 全图待查询的地面像素合计3319677，框内521715，框内仅占15.72%。
- bbox覆盖图像面积的中位数4.56%。
- 3条框内没有待检查地面像素，仍然支付了全图检查成本。

这表明约84%的待检查像素落在目标框外。它不是84%的整个规划时间，像素检查成本
也不完全相同；这里不将它换算成未经测量的整链路加速比。

普通成功样本 `s23-p00171`，原规划2.745秒，cProfile诊断3.297秒，其中
safe_floor_mask累计2.531秒；原生最短路包装函数172次共约0.0047秒。
对这类任务，ROI计算比优化最短路查询更有价值。

建议：仅对原bbox及法向计算所需的像素邻域执行昂贵的NavMesh检查，保持框内候选
采样、排序和目标支持判定一致，保留完整原始深度用于追溯。需要明确mask的ROI范围与
格式版本，不能让框外未计算的像素被下游误当作障碍。当前源码未发现训练侧直接读取
该mask的消费者，但它是已保存的诊断产物，仍需显式处理格式契约。

## 二、已有点净空缓存，但边与走廊计算仍大量重复

当前 `ClearancePlanner` 只缓存点的净空值。`edge_clear` 每次仍重新采样、snap、
构造小NumPy数组、检查高度、步进连接及阈值；`_in_corridor` 每次重新计算同一参考
折线的segment delta、长度平方及点到全部segment的距离。

诊断副本对原函数添加计数，不改变返回结果；慢任务各截断到12秒，因此下表是该
执行片段，不是完整任务全程：

| 样本 | 同配置、同有向端点的边检查重复率 | 同走廊、同点判定重复率 | 已有点净空缓存命中率 |
| --- | ---: | ---: | ---: |
| 慢成功 | 77.7% | 80.8% | 63.6% |
| 慢拒绝 | 92.0% | 82.9% | 94.0% |

跨点缓存/浮点表示归一化可能额外复用的原生净空miss不足约1%（本诊断片段）。
因此优先缓存完整的边验证和走廊判定，单纯扩大净空点缓存未必解决主要开销。

在捕获的10000次真实走廊查询序列上，保持相同布尔结果：

| 样本 | 原判定 | 预计算折线常量 | 预计算+精确查询memo |
| --- | ---: | ---: | ---: |
| 慢成功片段 | 0.265秒 | 0.232秒 | 0.043秒 |
| 慢拒绝片段 | 0.298秒 | 0.233秒 | 0.045秒 |

这是单函数微基准，未计一次性建表和内存成本，不代表完整规划或生产已提速6倍。

建议抽象：

- `CorridorGeometry`：每条参考折线的不可变预计算量，以及有界的精确点判定缓存。
- 任务级 `GeometryQueryContext`：统一管理查询统计、点/边缓存和内存额度。
- 复用现有 `NavMeshContext`、`PlanningContext`，避免把缓存散落到候选循环中。

边缓存必须包含NavMesh身份、完整校验配置、精确端点和方向，不能将A→B与B→A
视为必然等价；更不能把0.15m舒适净空检查当作0.05m检查的同一缓存项。
先使用任务级有界缓存，结束时释放。缓存路径仍检查取消/预算，显式处理预算计数
语义，避免将跳过计数误当作性能提升。

## 三、长尾不只是路线长，而是反复搜索类似失败

选择了普通成功、慢成功、慢拒绝和预算耗尽四类真实任务做函数级剖析。
普通成功执行完毕，另外三类最多运行20秒；cProfile有开销，截断不改变生产回执，
也不表示这些输入在20秒内不可达。

| 样本 | 原规划耗时 | 已保存的实际过程 |
| --- | ---: | --- |
| 普通成功 s23-p00171 | 2.75秒 | 138个候选，第一次规划选择通过 |
| 慢成功 s04-p00161 | 42.70秒 | 首候选测地距离3.35m，尝试23次才通过 |
| 慢拒绝 s34-p00074 | 49.73秒 | 首候选测地距离1.52m，59次均未在净空走廊内找到路线 |
| 预算耗尽 s13-p00197 | 92.74秒 | 首候选测地距离3.75m，未完成选择 |

短目标也会产生长尾，不能通过恢复8米限制来解决。

慢成功前20秒诊断内：7次A*累计13.79秒，边验证8.61秒，走廊判定5.86秒，
平滑3.23秒。它们有调用包含关系，不能将这些累计时间直接相加。
慢拒绝20秒内已经调用18次A*，其中走廊判定149268次。热点是Python层的
重复几何计算与重复搜索；在这些片段中原生最短路包装函数总计仅数毫秒。

候选策略会把一个失败扩展为原候选及其局部目标调整，再对下一个候选重新规划。
当前配置最多12个原候选、每个至多4个调整点，上限至多60次选择尝试（另有64次总上限）。
相近终点常共享大部分路线，但目前每次都从起点重新搜索和验证。

建议在缓存之后研究共享起点的搜索状态/局部连接复用，或粗到细的候选调度。
如果设置分候选/分舒适档预算，必须保留“暂缓/预算耗尽”状态，不能标为几何不可达；
也不能只因路线绕远就剔除合法的可见目标。

## 四、规划路径与跟踪器的兼容性会触发重复重规划

慢成功样本的23次尝试全部使用最小0.05m净空规划。前22次中：
11次控制预演净空不够，11次预演碰撞，最后一次才通过。
大多数失败都发生在第21帧、同一个拐角附近；有的预演最小净空降至约0.007m，
另一些为0。最终通过路线的预演最小净空约0.071m。

这说明“几何折线已通过安全检查”不等于固定跟踪器可以按该折线安全转弯。
当前0.5m前视距离等固定跟踪参数，在狭窄拐角有切角风险；因果判断还需针对性
参数对照，但已确认反复修改终点没有消除前面共同拐角的失败。

本次128条selection报告中有177次 `preview lacks swept execution clearance`，
35次 `final surface path fails execution clearance`；这些是候选尝试数，不是独立任务数。
预演积分本身在慢成功20秒诊断中只累计约0.029秒，主要成本来自预演失败后重新寻路。

建议单列行为优化：在失败拐角附近做局部路径修复，或采用与曲率/净空匹配的跟踪
策略。预演与真实执行必须使用同一冻结profile。保持最小净空、实际零碰撞、终点在
原框和固定PointNav目标；不能通过省略预演或放松验证来提高通过率。

## 建议实施顺序

1. **第一批：消除冗余几何计算。** bbox ROI查询；走廊常量及精确点判定缓存；
   同配置有向边验证缓存。优先保持框内候选、路径和安全判断等价，mask范围显式版本化。
2. **第二批：减少长尾重复失败。** 用上述两个真实反例验证共享搜索/连接复用，
   以及跟踪器兼容的局部修复。将改变路线、候选顺序或控制行为的改动独立成版本。
3. **后续：场景级预计算图或不同净空的预处理资产。** 有望减少Python细网格A*，
   但会改变离散化与覆盖率，需要专门验证楼层、窄通道、固定起终点连接及R2R参考顺序。
   不宜与第一批低风险优化混在同一变更中。

增加worker或把规划部署到Ubuntu可以增加容量，但不减少这里的重复工作。
建议先完成第一批CPU只读对照，再决定本机/远程资源配置。

## 验证与准入

先用冻结输入做配对只读规划：成功、无候选、净空搜索失败、预演失败、预算耗尽
分别分层，补充全部61场景、R2R及长测地路线。只对基元计算优化要求候选/几何判断
一致；预算耗尽转为成功的案例单独计数，明确预算计数版本。

记录均值/P95/P99、超预算率、CPU时间、查询/边检查唯一数、缓存内存与命中率，
同时检查目标仍在原框、路径与预演净空、终点误差、实际控制时长、失败类型和
长路线覆盖率。规划变快之后还需观察审计及存储是否成为新的瓶颈。

最后使用新身份、新起点做独立小批端到端录制核验，不重放旧运动。
通过后再冻结新部署；当前生产继续使用现有版本，本次未热改或重启。
