# C++ 主线与全链路优化复查

本报告记录 v4 首次设为默认及优化方向。后续已完成任务级查询缓存和原生路径核，
主线更新为 v5；freespace 工作按用户要求暂缓。见
[v5 实现与验证](planning-query-path-optimization-20261115.md)。

主线默认改为 `collection-v4`，自由指令与 R2R chunk 共用 C++ 受约束 A*。
默认值统一来自 `config.CURRENT_PLANNING_PROFILE`；采集配置、规划请求和示例一致。
C++ 扩展改为构建必需项，编译失败不出包；采集和规划服务启动时检查内核，
在创建尝试或消费模型结果之前暴露缺失依赖。v2/v3 的显式请求继续保留。

本次“进主线”是源码、默认配置、构建和部署准入的切换。正在运行的十万条生产任务
继续使用原冻结源码与配置，没有热更新、停止或重放。后续生产使用新冻结包启动。

159 项 sim-engine 测试通过；nav-train 1147 项通过、12 项跳过；harness 311 项及
4 个 subtests 通过，相关 Ruff、mypy、未定义名检查和前端构建通过。

2 条移动前剔除，R2R 审计通过，参考几何查询不增加仿真操作。

## 当前链路与测量边界

```mermaid
flowchart LR
  S[场景预算与滚动窗口] --> O[Simulator 四视图 RGB-D]
  O --> M[模型读取原始四图并画框]
  M --> F[深度反投影与框内可通行掩码]
  F --> G[候选落点与局部调整]
  G --> P[C++ A* 与净空边检查]
  P --> L[平滑与只读控制器预演]
  L --> E[冻结目标与一次性执行凭据]
  E --> R[4Hz 仿真与录制]
  R --> A[独立审计与 PointNav 目标]
  A --> D[待审核数据]
```

这是自由指令链路；R2R 从有序引导点进入同一规划器，规划后观测，模型标注可与
实际执行重叠。调度、几何、渲染、录制与审计属于 sim-engine；nav-train 保持
模型请求、生产预算和训练数据组织职责。私有目标、路线和验收指标不进入模型请求。

下面的秒级热点取自此前 C++ v4 慢成功样例的 cProfile，包含剖析开销，累计时间
相互嵌套。毫秒级微测来自同一冻结观察帧，270×480、框内 546 个支持点，重复
15 次取中位数。它们用于选优化方向，不代表全场景分布或生产阶段延迟。

## 逐阶段结论

| 环节与当前实现 | 矩阵化 / 原生化方向 | 优先级与限制 |
| --- | --- | --- |
| 起点预算、场景窗口、队列 | 保持确定性预算与滚动窗口；观察队列、冷加载、常驻命中率 | 已有机制，主要是调度问题，矩阵化收益不明确 |
| 四视图观测，`simulation.observe` | 分离冷加载、GPU 渲染、传输、PNG/深度编码计时；复用相机标定与缓冲 | 中；同一观测已有一次 RGB-D 获取，避免重复渲染更重要 |
| 模型画框 | 测请求准备/上传、推理排队和模型计算；利用模型服务现有批处理 | 独立跟踪；不将生成策略混入几何 C++ 核 |
| freespace 深度投影与法线，`safe_image` | 缓存不可变像素偏移，保持 NumPy 批量计算；必要时只计算 ROI 与法线 halo | 中低；投影约 17.3ms，缓存偏移原型约 15.7ms，收益有限 |
| freespace 几何认证，逐点 snap / island / clearance | 共用精确查询缓存，批量 NavMesh 适配，再考虑融合原生循环 | 高；这是图像掩码里仍有逐像素调用的部分 |
| 框内分层采样，`visual_region` | 已用 NumPy nonzero、lexsort 分层选点；批量投影与反投影 | 中；优先复用已计算几何，保留候选与同分顺序 |
| 落点支持检查，`region.target_valid` | 有界距离矩阵，或一次建索引、多次精确半径查询 | 低到中；89 次调用累计仅约 4.48ms |
| A*，`planning._astar` | 原生搜索已进入主线；优先消除重复 snap，再考虑共享搜索图 | 高；慢例发现 99.12% 的 snap 输入重复 |
| 净空边检查，`clearance._edge_uncached` | 原生化边重采样、距离、阈值；通过共用 NavMesh 适配降低逐点跨语言调用 | 高；8876 次未命中边检查累计约 3.09s |
| 路径平滑，`clearance._smooth` | 原生化短路与顺序 fairing；独立投影、距离可批处理 | 高；23 次累计约 3.24s，与边检查时间重叠 |
| 只读预演，`tracking.preview` | 先减少失败路径的重复预演；曲率相关跟踪参数另立版本验证 | 算法方向高；单次预演便宜，23 次合计约 0.092s |
| 4Hz 仿真、JPEG/深度压缩与写盘 | 单独测编码与 I/O；可设计有界录制写入池 | 中；保持原始频率、每帧哈希、动作证据和封存语义 |
| 独立审计，`recording.validate_recording` | 批量 SE(2)/四元数/时序检查，保留逐文件哈希和深度验证 | 中；图像和压缩底层已是原生库，先量磁盘等待 |

## freespace：分别处理计算、显示与模型输入

当前模型读取四张原始 RGB；`safe_floor_mask` 在选框后只处理选中视角的框内区域，
掩码与点映射写入 NPZ，未作为绿色叠加图发送给模型。该函数不调用 GPU 渲染。
它包含两种成本：深度到世界坐标和法线的数组计算，以及地面像素的 NavMesh 认证。

**绿色叠加显示**可以使用 NumPy mask 索引或 OpenCV 的
[blendLinear](https://docs.opencv.org/4.x/d7/d1b/group__imgproc__misc.html)。
单帧 NumPy 原型约 0.73ms。显示侧无需额外仿真渲染，暂时没有为此增加 GPU 或
C++ 专用核的依据。渲染图必须保留 unknown、computed 与 safe 的区别，不能把
ROI 外未计算像素标成障碍。原始 RGB、深度和 mask 应分别保存，叠加图可再生成。

**掩码认证**更适合优化共享几何查询。反投影、叉乘和法线阈值已经运行在 NumPy
原生数组运算中；现有 ROI 已省掉大部分框外 NavMesh 工作。继续优化应集中到
snap/island/clearance 的重复查询和绑定调用。图像 ROI 裁剪还需保留法线邻域 halo、
完整像素坐标和相机标定；缓存预除焦距的射线会改变浮点运算顺序，需另测边界。
本轮偏移缓存原型只在一个观察帧验证过逐元素一致，尚未进入主线。

**若将 freespace 前置给模型**，则需要四视图全图计算、图像协议与语义质量的单独
评估。可先尝试只由当前深度生成的地面提示，最终目标仍经过框内三维认证。
NavMesh 顶视图不包含 RGB 可见性；楼层、遮挡、深度表面和净空检查仍要保留。
[Habitat PathFinder 文档](https://aihabitat.org/docs/habitat-sim/habitat_sim.nav.PathFinder.html)
说明顶视图是按高度切片的 NavMesh 栅格，不是相机可见掩码。

OpenCV [distanceTransform](https://docs.opencv.org/4.x/d7/d1b/group__imgproc__misc.html)
可以快速给出到图像零像素的距离，可用于图像区域内的候选提示；它的单位是像素，
不等价于米制三维净空或可达路径。二维最近点也可能落在不同楼层或遮挡表面上。
此类结果只作为候选，继续接受原框、观测深度、连通性和三维边检查。

## 当前最明确的机会：重复 snap

对同一个慢成功样例做了只读计数，未改变查询返回、计划、候选或预算进度：

- 23 次原生搜索调用 snap 共 150,880 次；按实际 float32 三坐标字节计算，仅
  1,323 个不同输入，重复比例 99.12%。
- 单次搜索内部重复 127,891 次；不同搜索之间额外重复 21,666 次。
- 原生后端仍通过 Python 回调执行这些 snap，因此精确缓存可以同时减少绑定往返
  和 NavMesh 查询。这是调用次数的潜在减少量，尚未测得缓存实现的耗时收益。

建议先引入任务级 `NavMeshQueries`：由 `NavMeshContext` 持有，任务结束清理，
按 NavMesh 身份、操作参数和原始 float32 坐标缓存；容量有界。静态几何的不合法
返回可以缓存，运行错误和取消不能当作几何失败缓存。保留逻辑预算和取消检查。
避免在所有场景共用无身份隔离的全局字典。

先实现精确缓存与 `snap_many / clearance_many / island_many` 适配接口，再评估原生
批量实现。Python 包一层循环只能改善接口组织，不能自动消除逐点 C++/Python 往返。
真正融合查询需要受支持的 Habitat C++ 绑定或资产适配；当前 `_astar` 只依赖 CPython
稳定 ABI，不假设能够直接访问 Habitat 的内部指针。

## 矩阵算法与索引的适用范围

546 个支持点、96 个查询的原型结果如下，保持原有 3D 欧氏距离和 0.025m 阈值：

| 实现 | 第一次微测 | 后续独立微测 |
| --- | ---: | ---: |
| 逐查询 NumPy 扫描 | 2.687ms | 2.735ms |
| 最多 32,768 点对的矩阵块 | 1.984ms | 2.053ms |
| cKDTree 批量查询 | 0.102ms | 0.080ms |
| cKDTree 首次建树 | 10.398ms | 0.306ms |
| cKDTree 重复建树中位数 | 未测 | 0.092ms |

索引在重复查询时更合适，但首次建树、导入和维护成本不能忽略，且这一环节当前总量
只有毫秒级。不能用查询阶段约 26 倍的比值推算全链路收益。
[SciPy cKDTree.query](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.cKDTree.query.html)
提供批量查询；若采用，应使用 `eps=0`、单线程和原三维距离，并对返回候选按原
数值公式验证半径边界。小输入保留数组扫描，避免为数个点建索引。
本轮两组原型与逐点结果一致，尚未集成为正式 `SupportIndex`，也没有增加 SciPy 依赖。

[原型微测](evidence/planning-mainline-review-20261115/kernels.json)、
[独立复测与建树成本](evidence/planning-mainline-review-20261115/kernels-followup.json)。

平滑要保留更新依赖：当前 fairing 逐点更新，后一个点使用已更新的前一个点。
一次矩阵计算全部新点会改变算法。可以将顺序循环下沉 C++，将独立投影、距离和
候选预筛批量化；最终安全边检查及首个失败处的逻辑短路仍要保留。

## 算法层面的下一步

1. **共享候选图与搜索结果**：同一起点的相邻目标反复经过相同区域。先共用
   snap、边证书与局部图，再验证单起点多目标搜索。不同候选的参考走廊有差异，
   不能直接把一个走廊内的可行性结论套到另一个目标上；保留候选优先级和 R2R
   有序引导点、重复访问和楼层状态。
2. **减少控制器导致的重规划**：已有慢例中 23 次尝试只有最后一次通过，前面多次
   在相近拐角被预演排除。可另立控制器版本评估曲率相关 lookahead、拐角减速和
   局部路径修补。预演与执行必须使用同一版本，不能仅放宽预演使计划通过。
3. **粗路径引导细化**：保留 Detour 基础路径，用局部细化修复净空不足的路段，
   与全走廊网格搜索比较展开数、保留率和路径质量。属于算法变化，另立规划版本。

## 仿真、录制和审计的工程优化

A100 的 Pillow 已启用 libjpeg-turbo。`np.savez_compressed` 的压缩底层也是原生
实现；换成另一个 Python 包名不意味着减少同类编码开销。需要区分 encode、compress、
文件写入、哈希和磁盘等待，再决定有界写入池或新存储格式。

可以设计 `FrameWriter` 承接不可变帧，限制队列字节数，回传文件与哈希；全部写入
确认后才能封存并交给审计。4Hz 采样与控制时序、一次性凭据、运动前持久化证据、
不确定状态和不自动重试规则保持。移除 journal 的持久化屏障不属于性能优化方案。
更换深度压缩或分块格式需新录制版本及读取端迁移，保留旧格式读取。

审计中的位姿、四元数、时间轴可批量验证；仍需验证实际保存媒体、深度和终帧，
不能仅相信写入端回执。渲染、执行和这些 I/O 阶段目前没有 v4 全量生产的分项计时，
暂不为它们分配估算加速倍数。

## 建议实施顺序

下一轮先做 **任务级精确 snap 缓存 + 统一批量几何适配**，再做 **边采样与顺序平滑
C++ 核**。随后评估共享候选搜索和控制器拐角策略。图像叠加、支持点索引和投影缓存
按实际占比择机处理，不为毫秒级步骤增加一条 GPU 数据搬运链。

每轮都使用新冻结版本，比较普通、长尾、不可达、长可见路径和 R2R；同时记录
阶段 CPU/墙钟、预算终态、候选保留率、真实执行审计和数据大小。缓存/内核优化先做
结果对照，算法变化再做路径与质量比较；最终吞吐需要新的生产规模观测。
